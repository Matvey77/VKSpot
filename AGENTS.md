# Правила работы с VKSpot

## Контекст

- Начинай с этого файла и `package.json`; `README.md` — карта проекта.
- Читай только нужное: `PRODUCT.md` — инварианты, `docs/architecture.md` — модули, `docs/workflows.md` — интеграции, `docs/maintenance.md` — проверки и инструменты, `DESIGN.md` — интерфейс.
- Ищи через `rg`; не загружай весь репозиторий, lockfile, снимки, сборки или журналы в контекст. Детали поведения подтверждай кодом и тестами.
- Документы — короткие тезисы. Один факт хранится в одном месте; вместо повторов ставь ссылку. История изменений остаётся в Git.

## Изменения

- Сохраняй исходные записи, порядок, отдельные повторы, решения пользователя и Undo. Поисковый кандидат не равен подтверждённому назначению.
- `core` не зависит от Electron/React; SQLite, сеть и файлы принадлежат main; renderer работает через типизированный Bridge. IPC проверяет отправителя и входные данные.
- Не добавляй обязательные платные сервисы, телеметрию, секреты или реальные пользовательские данные в исходники и тесты. Проверки используют изолированный `VKSPOT_DATA_DIR`.
- Упрощай доказанно лишний код и зависимости; сохраняй читаемость, совместимость архивов и функций. Не минифицируй исходники ради количества строк.
- Для UI основной навык — Impeccable. Сохраняй дизайн-систему и явный выбор пользователя. Magic UI — только по задаче; Emil Kowalski — для взаимодействий/анимаций. Общие дизайн-навыки не смешивай без причины.

## Экономия ресурсов

- Небольшие задачи выполняй сам, если делегирование дороже работы.
- Для независимых рутинных подзадач выбирай доступную дешёвую модель, например GPT-6 Luna. Передавай узкую задачу, нужные пути и краткий контекст; не копируй всю историю.
- Сложные решения, безопасность, миграции и итоговую проверку оставляй основной модели. Проверяй результат подагентов; не запускай агентов и проверки без полезной цели.
- Объединяй независимые чтения и проверки. Не повторяй успешные проверки без новых изменений или обнаруженной проблемы.

## Завершение задачи

- После каждого завершённого логического изменения проекта делай коммит с понятным описанием. Изменение — цельная проверенная задача, а не отдельное сохранение файла. Перед финальным ответом свои изменения должны быть закоммичены; чужие правки не включай без разрешения. Push — по запросу.
- После изменения приложения создавай новую Windows-сборку: обнови версию в `package.json` и lockfile, выполни `npm run dist:win`. Документация без изменения приложения новой версии не требует.
- Версии: patch — исправления, оптимизация и небольшие правки UI; minor — новые возможности; major — несовместимые изменения. До 1.0 несовместимые изменения повышают minor. Одной логической задаче соответствует одна версия и финальная сборка после всех правок.
- Проверяй форматирование, lint, типы и затронутое поведение. Для выпуска запускай unit; E2E выполняй на готовом EXE. Новые тесты добавляй для рисков поведения; для простого оформления достаточно существующих проверок и визуального осмотра.
- Перед коммитом проверь diff и исключи профили, секреты, временные артефакты. В финале укажи результат, проверки, версию/путь сборки и коммит. Если проверка или сборка не удалась — сообщи прямо.
